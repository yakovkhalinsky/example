    1. Guestbook — stored injection

    Posts are saved (in your browser's local storage) and rendered into the page. In vulnerable mode the rendering uses innerHTML, so markup in a post becomes live page content — for every later visit, too.

    👉 Payloads for this panel go in the Comment field below.

    Why it works / the fix

    The app builds HTML by string concatenation and assigns it to innerHTML, so the browser parses attacker text as markup. Event-handler attributes (onerror, onload…) execute; a <script> element inserted this way does not run — that's why the library's script-tag payload is the control case. Fix: insert text with textContent (or escape output), so input is data, never markup.

    2. Profile preview — HTML, attribute and URL injection

    A “live preview” card built from four fields. Name and bio go into HTML, the avatar URL goes into an <img src="…"> attribute, and the website goes into an <a href="…"> — three different injection contexts, three different payload shapes.

    👉 Payloads for this panel go in the Bio, Avatar image URL or Website field — each payload card says which.

    Why it works / the fix

    Same innerHTML mistake, more contexts: a quote breaks out of the avatar attribute (x" onerror="…), and a javascript: website URL turns the link itself into code that runs on click. Fix: build nodes with DOM APIs and textContent; set attributes with setAttribute (values can't break out); and allowlist link protocols (http:/https: only) — setAttribute alone does not make a javascript: href safe.

    3. Reflected injection — the greeting

    The page greets whoever the ?name= URL parameter says. That's the classic reflected pattern behind phishing links: the payload rides in the URL and executes in the victim's browser on a trusted page. Type a name (or a payload), build the link, and open it.

    👉 Payloads for this panel go in the Name in the URL field below, then open the test link.

    Why it works / the fix

    The greeting is filled with innerHTML straight from the query string — no server round-trip needed for DOM-based reflection. Fix: same rule: textContent for text, always, no matter where the string came from.
